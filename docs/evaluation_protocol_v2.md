# 验证协议 v2：非劣效设界 + 成本模型 + kill test 判定树

> **状态**:评审修订版 · 配套 `memory_three_layer_design.md`(设计)、`positioning_and_related_work.md`(定位/相关工作)、`v1_implementation_guide.md`(实施)。
>
> **本轮修订动因(重要)**:原设计把"解决记忆膨胀/省 token"当卖点之一,但**该 claim 在本架构下不成立**——复盘 agent 是新增 LLM 成本,L3 全量注入可能比基线更贵。本文件重写验证协议,把论文主线从"更省"修正为 **"成本有界 + 不高于基线的预算下注入质量 + 遗忘保护正确性"** 三 claim 体系,并给出非劣效设界、成本分账模型与 kill test 判定树。

## 0. 主线修正(先读这一节)

### 0.1 为什么"省 token"不能作为 claim

三层记忆相比基线(v0.3.1 平权注入)引入两笔**新增成本**:

| 成本侧 | 来源 | 基线是否有 | 量级(待实测) |
|---|---|---|---|
| 写入侧 | 复盘 agent 读 full_states_log JSON(分析师报告 + bull/bear 全文 + risk 全文 + trader 计划 + 决策)做 deep LLM 调用 | 无 | 输入约 2–4 万 token/次,输出几百 token |
| 注入侧 | L3 准则 preamble(若全量 50 条)+ L1 top-k | 无(基线只注入 ≤8 条决策日志+反思) | 50 条准则可能 ≥ 基线注入量 |

**结论**:论文的"效率"卖点不能写成"省 token / 更便宜",否则会被 ACON(微软,压缩记忆省 26–54% token)、SimpleMem(省 30 倍推理 token)等**真压缩**工作直接击穿——它们没有复盘 agent 这笔新增写入成本,量纲不同,比不过。

### 0.2 修正后的 claim 体系(C1–C3,由强到弱)

- **C1 有界性(最稳,必保,对抗"膨胀"动机)**:
  - 记忆文件大小/解析成本有**硬上限**(`max_event_entries=200` + `max_rule_entries=50`),不随 run 轮数增长;
  - 基线决策日志 `load_entries()` 全文解析是 **O(日志大小) 线性增长**,`_apply_rotation` 只约束 resolved 数;
  - 度量:lessons 文件解析耗时 vs run 数曲线(新方案趋于平台),决策日志解析耗时 vs run 数(线性上升)。
  - **这是"成本可预测/可扩展",不是"成本更低"**——严格、可测、不怕反驳。

- **C2 等预算或更低预算下的注入质量(主攻,对抗 ATLAS 反证)**:
  - **注入预算不高于基线**的前提下,事件级选择性注入(L1)+ 准则(L3) vs 基线平权注入(n_same=5+n_cross=3 决策日志反思),**方向命中率非劣效或更优**;
  - **即使持平也算赢**:持平 + C1 有界性 = 可发表的系统贡献;提升是惊喜;
  - 这是对"记忆注入无益"(ATLAS 反证)的第一道防线——我们不 claim 记忆让 agent 更聪明,claim **在不多花上下文的前提下**注入内容更相关。

  > **口径修订(2026-09-13,先于 P1 运行注册)**
  >
  > 本 claim 原写作"**固定**注入 token 预算下"。改为"**不高于**基线"的原因:两臂实现为**等预算替换**(`experiment_plan.md` §2.4)——L1 段与 legacy 段**二者取一**,而 L1 是压缩摘要,实测注入量只有基线的 **69%**(7,119 vs 8,299 字符,测试场景 `600519.SS @ 2026-07-13`;另两例为 54% / 76%)。
  >
  > **为什么这不算事后放宽口径**:
  > 1. 修订依据是**与结果无关**的上下文量测量——当时 P1 尚未运行,不存在任何命中率数据;
  > 2. 方向是**收紧而非放宽**:主张从"同等预算下不劣"变为"**更低**预算下不劣",更难满足,不是更容易;
  > 3. 另一条路(把 `on` 臂预算调高到与基线对齐)才是看着数据调参,已明确排除。
  >
  > **报告要求**:每次 run 的真实 `past_context` 已存档在 `full_states_log_<date>.json`,论文必须报告**两臂实测注入字符/token 及其比值**,而不是只声称"预算不更高"。

- **C3 遗忘保护正确性(机制 claim,不依赖 LLM 效果)**:
  - 极端事件(大亏,`|alpha| ≥ event_protect_threshold`)受**保护集 + 方向下限**保护,不被常规淘汰误杀;
  - 基线"丢最旧"会优先丢掉一年前的大亏;
  - 这是与决策质量无关的**工程正确性**,通过单测 + 构造数据即可证明,不需要跑 A/B。

### 0.3 与压缩方法(ACON / SimpleMem / Compressed Context Memory)的边界

- 它们做**表示压缩**(KV 缓存 / 上下文蒸馏),你做**记忆选择与治理**(存什么、忘什么、注入什么)——机制不同 → **不作为对比基线**;
- 引用目的:① 证明"记忆/上下文成本治理"是活跃且被顶会认可的题材(选题合理性);② 明示差异:"我们不做表示压缩,做存储层选择,两者互补";
- **不声称压缩更优、不声称省 token**;若审稿人问"为何不与 ACON 比",答:"ACON 压缩的是上下文表示,我们选择的是存储内容,优化对象不同;我们的注入预算**不高于**基线(实测为基线的 69%),证明的是同等或更低预算下选择的价值"。

## 1. 成本模型(写入侧 vs 注入侧分账)

### 1.1 指标定义

| 指标 | 定义 | 度量位置 | 与基线的关系 |
|---|---|---|---|
| 注入侧每 run token | L3 preamble + L1 top-k 注入 PM 的 token 数 | `_build_past_context` 前后计数 | 目标:与基线注入量**同量级或更低**(对齐预算,非劣效前提) |
| 写入侧摊薄成本/run | 复盘 agent 单次成本 × 触发率(结算中 |alpha|≥阈值 占比) | `_resolve_pending_entries` + `cost_log.csv` | 基线为 0,这是**新增成本,必须如实报告** |
| 解析有界性 | lessons 文件解析耗时 vs run 数曲线 | 基准测试 | 基线线性增长 vs 新方案平台化 |
| 总 API 成本对比 | 单臂全链路 API 账单 | `cost_log.csv` | 如实报告,不做"更省" claim |

### 1.2 计算框架(数字待实测填充,禁止预估代替)

- **单次复盘 agent 成本** = (full JSON 输入 token + 摘要输出 token) × 单价;full JSON 大小**必须实测**(在受限网络 + A 股池下跑一次量);
- **触发率** = 结算样本中 |alpha| ≥ `event_alpha_threshold`(0.05) 的比例;若 5–15% → 摊薄成本低;若 >30% → 需上调阈值或改 quick 档,否则写入侧成本失控;
- **注入侧预算目标**:事件段 N=5(已实现)与基线 n_same=5+n_cross=3 同量级;**L3 准则禁止全量 50 条注入**——v2 的 `get_rules_context` 应按相关度截断(如 top-10)或压缩单条长度,否则注入侧反而变贵;
- **记录字段**(cost_log.csv 扩展):provider、model、ticker、date、rounds、input_tokens、output_tokens、cache_hits、cost、decision。

## 2. §8 验证协议重写(非劣效设界)

> 覆盖 `positioning_and_related_work.md` §6 的协议草案中"指标"部分;配对结构、时间一致切分、交易成本、可复现等其余条款沿用。

### 2.1 主指标与配对结构

- **主指标**:方向命中率(评级方向 vs 已实现 alpha 符号),二分类;
- **配对**:固定 (ticker, date) 列表(日期靠后、收益已实现、yfinance 确定性可得),**同臂内多轮**(≥3,应对 LLM 采样噪声),双臂 = 基线平权 vs 三层记忆;
- **消融分层**(可选扩展):v1-only(L1)、v1+v2(+L3)、v1+v2+v3(+L2),逐层看注入质量贡献。

### 2.2 非劣效界 δ 的设定(实验前写死)

- **默认 δ = 0.05(绝对 5pp)**:方向命中率的实际差异 <5pp 对交易决策无实质意义,低于此视为"无实际差异";
- 备选:δ = 0.2 × p0(基线命中率的 20%),若 p0 已知且明显偏离 0.5 可选用;
- **硬性纪律**:δ 必须在实验前设定并写入实验日志,**禁止看结果后回调**(审稿人红线,ESWA 综述的审计口径);
- 若基线 p0 本身接近 0.5(随机水平),说明基线弱,非劣效界应更严(如 0.03),避免"对一个随机基线持平"被当贡献。

### 2.3 统计检验

- 每配对点单轮命中(0/1) + 多轮重复 → **配对比例数据**:用 **McNemar 检验**(配对二分类,双臂同一配对点)或配对 t 检验(每配对点多轮命中率均值);
- **非劣效判定**:双臂命中率差值的 **90% CI 完全落在 (-δ, +δ)** → 非劣效成立(TOST 逻辑);
- **提升判定**:差值 **95% CI 下界 > 0** → 显著提升;
- **样本量预计算**:配对 t 检验近似 N = (z_0.975 + z_0.8)² · σ_d² / δ²;σ_d = 配对点间命中率差值的标准差,**用基线臂 20 配对点 × 3 轮实测**;α=0.05,power=0.8;
- 每个数字可复现:固定 provider/model/温度/种子/数据版本(release 代码 + 配置)。

### 2.4 kill test 判定树(最小实验,决定是否继续)

```
kill test = 20 配对点 × 3 轮 × 双臂,跑完填判定树
│
├─ 方向命中率差值 95% CI 下界 > 0(显著提升)
│     → 主线 C2"不高于基线预算下更准"成立,追加消融 → 投 NLPCC(CCF-C)
│
├─ 差值 90% CI 完全落在 (-δ, +δ)(非劣效)
│     → 主线 C1"有界性"+ C2"持平即赢"成立 → 投 NLPCC / 正规 EI
│     → 前提:写入侧成本如实报告且可接受(触发率 ≤ ~30%)
│
├─ 差值 95% CI 上界 < -δ(显著劣化)
│     → 诊断:是注入干扰(内容质量)还是检索错误(取错条目)?
│        ├─ 检索错误 → 修 bug 重测
│        ├─ 注入干扰 → 降 L1 注入条数 / 调准则长度,重测一次
│        └─ 仍劣化 → 放弃 C2,收缩为纯 C1+C3(有界性+遗忘保护)
│           系统论文,投正规 EI;或换题
│
└─ 成本维度(独立判定,两条主线都要过):
     写入侧摊薄成本/run 是否可接受?
        ├─ 触发率 >30% → 上调 event_alpha_threshold / 换 quick 档
        └─ 注入侧 L3 全量 > 基线 → 截断 top-10 或压缩单条
```

### 2.5 kill test 的最小成本估算(供预算,数字待实测)

- 20 配对 × 3 轮 × 2 臂 = 120 runs(主流程)+ 复盘 agent 按触发率叠加;
- 主流程单 run ≈ 5 万输入 + 1.7 万输出 tokens(社区实测量级,待本机复核);
- 用 DeepSeek-chat(¥2/¥8 每百万):主流程约 ¥43 量级(详见对话估算,按实测单价重算);
- **先跑 5 runs 实测单 run token 与金额,再外推总预算**(不要直接拿估算值当预算)。

## 4. 执行顺序(v1 已实现,直接跑)

1. **基线量化**:基线臂 20 配对点 × 3 轮,得 p0 与 σ_d(算样本量);同时量决策日志解析耗时 vs run 数;
2. **成本实测**:`cost_log.csv` 已有;补复盘 agent 单次输入/输出 token 计数;量 lessons 解析耗时;
3. **kill test**:处理臂同 20 配对点 × 3 轮,填 §2.4 判定树;
4. **按判定结果定主线**:显著提升 → C2 主攻;非劣效 → C1+C2;劣化 → 收缩 C1+C3;
5. 主线定了再决定 v2(L3 蒸馏)/ v3(L2 检索)是否值得投入(它们只增强 C2,不增强 C1/C3)。
